账号资料与头像技术说明

本人资料只修改昵称、姓名和头像；保存时发送变化字段，完成独立回读后才更新页面。

这里是登录账号本人，不是家人 / 宠物档案。邮箱和手机号仅展示，不能直接套用完整 UserDTO 写入。

1用哪些接口

  1. 获取本人资料GET/user/info进入页面、保存前及保存后读取
  2. 保存变化字段PUT/user/personal/edit原 username + nickname / name / avatar 差量
  3. 上传图片POST/sys-file/uploadmultipart/form-data，part 名称 file
  4. 展示返回头像GET服务端返回的头像 URL动态返回 URL，使用不带 Token 的图片客户端

上传的实际调用为 multipart；公开文档中的 application/json 声明仍有差异。头像地址按环境和允许的来源校验，不向任意图片地址附带登录 Token。

2保存和上传怎么走

  1. 加载资料

    GET /user/info，保存当前账号、环境、username 及字段基线。

  2. 编辑与预览

    昵称 / 姓名单项编辑；图片先本地预览，确认后才读取文件并上传。取消不发送保存请求。

  3. 提交变化

    保存前重读资料以发现冲突；头像先上传取得地址，再 PUT 原 username 和变化字段。

  4. 确认成功

    再次 GET /user/info，逐项核对本次变化；一致后更新资料页及“我的”展示。

3哪些字段可以改

字段 / 区域来源 / 内容处理规则
昵称nickname当前客户端最多 80 个字符；空串可清空，不能用页面显示的兜底姓名覆盖原值。
姓名name当前客户端最多 80 个字符；只提交本次变化，空串与 null 分别处理。
头像avatar保存服务器返回的合法地址；移除发送空串。照护对象接口对应字段则是 avatarUrl。
用户名username带上保存前回读的本人原值；这是写入所需字段，不提供改用户名入口。
只读信息email、phone 等显示已有信息，不提交手机号、邮箱、地区、联系人或完整 UserDTO。
图片限制PNG / JPEG，最多 5 MiB校验文件签名、MIME 和解码尺寸；单边最多 8192、总像素最多 3200 万，当前不自动压缩。

4失败时怎么处理

  • 冲突

    待改字段或 username 与编辑基线不同，停止提交并要求刷新，避免覆盖其他入口的修改。

  • 保存未确认

    写入后超时、取消或回读不一致时先刷新资料，再允许继续保存，不自动重放写入。

  • 头像部分成功

    已经确认上传的地址可在同一上下文复用；上传本身未确认时不盲目重传同一图片。

  • 切账号或环境

    请求前后核对身份，清理或隔离缓存；旧账号头像不能写入新账号。

5哪些内容还要补

  • 接口问题

    后端仍需明确公共资料接口的 App 使用范围；缺 username、非空 phone 的错误及清空语义需修正 / 确认。

  • 文件策略

    头像公开读取、地址有效期、替换后的旧图及上传后未引用文件的回收规则待确认。

  • 验收边界

    本人头像的 JPEG、真实弱网和过期会话异常尚未完成真机验收；不能将客户端格式支持等同于端到端通过。

  • 既有证据

    10-09 本人昵称 / 姓名及 PNG 头像有保存、独立回读和重新登录记录；文件回收、本人 JPEG 和异常会话不随本文更新而新增通过。

公共约定：业务请求带 Bearer Token 与 IANA 格式的 X-TimeZone；ID 保持无损，写入结果不明时先回查。认证、图片等专用客户端按各自规则处理。
